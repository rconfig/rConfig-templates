# CLAUDE.md

## What this repo is

Community connection templates for rConfig V8 Core and Pro.

## Working rules for any Claude session in this repo

- Work is governed by Stephen's action plan. No work outside an approved item.
- Never commit or push without Stephen's explicit go for the specific change.
- Deviations: stop, describe the deviation simply, wait for approval.
- `restructure/v2` is read-only reference. Never merge or cherry-pick from it.
- Report changes as concise diff summaries.

## Code and content standards

This is a living section. It is seeded now and extended as standards are adopted.

- Markdown and YAML comments use the ASCII hyphen only. No em dash, en dash, or other Unicode dashes.
- All free-text YAML values are wrapped in double quotes.
- Filenames and directories are lowercase and hyphenated. See Template file naming below for the full convention.
- Vendor directories are named for the lowercase common short form of the vendor name. Examples: `palo-alto`, `edgecore`, `checkpoint`, `digi`, `rad`.
- Directories prefixed with an underscore are reserved for non-vendor content that must sort above the vendor listing. `_base` holds the starter template.
- Commit messages use the plan item prefix `P<phase>.<item>`, for example `P1.1`.
- `pagerPrompt` and `pagerPromptCmd` are deprecated and must not appear in templates. Both values are ignored.
- Every adopted standard MUST be added to this file in the same change that adopts it.

### Template file naming

Convention:

```text
<vendor>-<osfamily>[-<versionqualifier>]-<protocol>-<authmode>[-<variant>].yml
```

- `vendor` matches the directory name.
- `osfamily` is the OS or CLI family, never a hardware model. It may be omitted only when the vendor has a single uniform CLI.
- `versionqualifier` is used only where the vendor has real version differences in connection behavior. Example: `panos-9x`.
- `protocol` is `ssh` or `telnet`. `script` and `tl1` exist for Pro templates.
- `authmode` is `enable` or `noenable`, with `nousername` as an additional variant where relevant.
- `variant` covers agent or mode specifics such as `vector`, `noninteractive`, `banner`, `vdom`.
- Variants may chain when a template genuinely carries more than one. Example: `-noninteractive-vector`.
- `authmode` is omitted for protocols that have no enable concept, such as `tl1` and `script`.
- Hardware models appear in a filename ONLY when the model itself changes connection behavior. Example: `hp-1920` keeps its model number because the 1920 requires a special elevation command that other HP switches do not.
- The vendor prefix is deliberate even though it repeats the directory name: filenames travel without their paths (downloads, imports, attachments) and must be self-identifying.
- All lowercase, hyphens only, no underscores or spaces.

### Template header

Every template starts with the standard header below, generated by
`scripts/apply_headers.py`. The script is idempotent and preserves existing `Status` and
`Tested-on` values on rerun, so verification results are never overwritten.

```text
# rConfig connection template
## Edition: <core|pro>
## Status: <rconfig-verified|community-tested|untested-starter>
## Tested-on: <rConfig versions and editions the template is known to work on>
## Replaces: <old filename, renamed templates only>
## Docs: <documentation URL>
## Community: https://github.com/rconfig/rConfig-templates
## Note: all free-text values must be wrapped in double quotes " "
```

- `Replaces` appears only on templates renamed during the restructure, sourced from
  `docs/MIGRATION.md`.
- `Edition` is `pro` when the protocol is `script`, `tl1` or `xftp`, or when the template
  uses `sshPrivKey`. Everything else is `core`.
- `Docs` is the Script Integration Engine URL for `script` protocol templates and the
  connection templates URL for everything else.
- Vendor specific comments are preserved and re-emitted directly below the header.

### Line endings

All `.yml` and `.md` files use LF line endings, enforced by `.gitattributes`.

## Releases and tagging

Adapted from the process in the v8core repository. The template library is versioned because the
product pins it: a seeder or an import that references a path needs a ref that does not move.

- **Use annotated tags, `vMAJOR.MINOR.PATCH`**, for example `git tag -a v2.0.0 -m "..."`. This
  repository is standalone, so tags are unprefixed. Never create a lightweight tag.
- **The version lives in two places and both are bumped together**: the root `VERSION` file and
  the newest heading in `CHANGELOG.md`. Do this before tagging, not after.
- **Semantic versioning applies to paths, not to content.** A renamed or deleted template is a
  MAJOR change, because it breaks anything pinning the old path. A new template or a corrected
  display name is MINOR. A comment or documentation fix is PATCH.
- **Never move or re-point a pushed tag.** If a published tag is wrong, leave it and correct it
  in the next release.
- **Every rename and deletion goes in `docs/MIGRATION.md` in the same change that makes it.** The
  migration map is what a pinned consumer follows when it upgrades.
- **A release is not finished when the tag is pushed. It needs a GitHub Release too.** Publish
  with `gh release create vX.Y.Z --title "rConfig Templates X.Y.Z" --notes-file <file>
  --verify-tag`.
- **Release notes are not the CHANGELOG entry.** The release body is condensed one-line bullets
  under the Keep a Changelog headings that apply, ending with `See CHANGELOG.md for detail.`
  Lead with any action a consumer must take, such as re-pointing pinned URLs.

### Merging a PR to main

1. Confirm CI is green on the PR.
2. Merge with a merge commit, so `git log --follow` keeps working through renames.
3. If the merge changed any path, bump `VERSION`, date the `CHANGELOG.md` entry and confirm
   `docs/MIGRATION.md` covers every rename and deletion.
4. Commit the version bump, create and push the annotated tag, then publish the GitHub Release.
5. Tell the product side which tag to pin.

### The frozen master branch

`master` is pinned at `3f162e7`, the last pre-restructure commit, so fielded installs with baked-in
`raw.githubusercontent.com/.../master/...` URLs keep resolving against the tree they were written
against. **Never push to `master`.** It is a compatibility shim, not a branch.

## Verification

The validator MUST pass before any template change is reported complete.

```bash
python3 scripts/validate_templates.py
python3 scripts/apply_headers.py --check
```

The validator exits 0 when clean and 1 on any ERROR. Warnings do not fail the run: each one is
a known deviation with a decision still pending, listed in the temporary allowlist at the top of
the script. Both commands also run in CI on every push and pull request, see
`.github/workflows/validate.yml`.
